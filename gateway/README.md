# Mast gateway (ESPHome, ESP32-S3 + Ethernet)

Reads the three sector scanners' protocol 3 stream (protobuf buckets every 200 ms,
[`../scanner_fw/PROTOCOL.md`](../scanner_fw/PROTOCOL.md), schema
[`../scanner_fw/proto/bletracker.proto`](../scanner_fw/proto/bletracker.proto)) and publishes
it to MQTT (layout v3, below): one RSSI message per sector per bucket, the raw advert and scan
response bytes split into Theengs-style fields, status, counters, events and a separate
security stream. The RX pin a scanner is wired to is its sector; the gateway watches each pin's
chip ID for a board swap, keeps the settings the scanners forget at boot applied, passes commands to the scanners and
lowers their byte budget when it can't keep up. Needs scanner firmware **0.4.0 or later**;
older (v2) frames are dropped as bad.

Home Assistant sees only the gateway's own entities, over the ESPHome API: health sensors,
the chip ID and a mismatch alarm per sector, the self-test result and a few buttons. There
are no Home Assistant entities per beacon, and MQTT carries only the beacon data, events and
commands (MQTT discovery is off).

- `example-mast.yaml`: the per-mast device config. Copy it once per gateway (e.g.
  `bletracker-garage.yaml`) and set the mast ID, name and API key secret; it stays on DHCP
  unless you uncomment its static IP block.
- `packages/bletracker-gateway.yaml`: everything shared by every mast, for the Waveshare
  ESP32-S3-ETH (pins from its [pinout](https://docs.waveshare.com/ESP32-S3-ETH), all in
  `substitutions`). The mast files pull it in with `packages:`; it is not a device config on
  its own.
- `components/sector_scanner/`: external component, one hub per mast with one `sectors:`
  entry per scanner RX pin. `pb_wire.h` is a small protobuf wire-format reader/writer (no
  code generator needed); `selftest_data.h` is generated by `tools/make_selftest.py`.
- `tools/make_selftest.py`: builds the boot self-test data from the reference protobuf code
  (see "Self-test").
- `secrets.example.yaml`: copy to `secrets.yaml` (or use the ESPHome dashboard's secrets).

Each mast needs its own `mast` ID: it goes into the MQTT topics (`bletracker/<mast>/...`) and
the device name (`bletracker-<mast>`), so two gateways never share topics or a Home Assistant
device.

```yaml
# bletracker-garage.yaml
substitutions:
  mast: garage
  name: bletracker-${mast}
  friendly_name: BLE Tracker Garage
  api_key: !secret api_key_garage

packages:
  gateway: !include packages/bletracker-gateway.yaml
```

## Build and flash

In the Home Assistant ESPHome add-on: copy `components/`, `packages/` and your mast file(s)
into the add-on's `config/esphome/` folder, then Install the mast. First flash over the S3's
USB-C; later ones over Ethernet (OTA). Then add the device in Home Assistant's ESPHome
integration (API key from your secrets).

From a PC, ESPHome must build in a path without spaces (like the scanner firmware), so copy
this folder somewhere like `C:\fw\gw-build` first:

```bash
esphome run example-mast.yaml
```

`example-mast.yaml` (protocol 3, layout v3) compiled clean with ESPHome 2026.9.0 on 2026-11-02
(RAM 24.7 %, flash 37.4 %). It has not run on a board yet; the boot self-test (below) is the
first check once it does.

## Wiring

All gateway wiring is on header pins 31-40 (pin numbers as printed on Waveshare's pinout).
Each scanner's D6 has its own gateway RX pin, and that pin is its sector. The gateway has one
TX that goes to every scanner's D7 through the bus board's TX row; commands carry the target
scanner's chip ID, so only that scanner acts on them.

| XIAO | Sector 0 | Sector 1 | Sector 2 |
| --- | --- | --- | --- |
| D6 (TX) → gateway RX | GPIO17 (34) | GPIO16 (32) | GPIO18 (31) |
| D7 (RX) ← bus TX row ← gateway TX | GPIO21 (35) | GPIO21 (35) | GPIO21 (35) |
| 5V ← bus 5V row | VBUS (40) | VBUS (40) | VBUS (40) |
| GND ← bus GND row | GND (38) | GND (38) | GND (38) |

VBUS is the USB-C 5 V, which is where the PoE splitter feeds the board. Kept clear: GPIO 4-7
(TF card), 9-14 (W5500), 0/3/45/46 (strapping), 19/20 (USB), 33-37 (octal PSRAM), 43/44.
GPIO1 and GPIO2 are free. Logs come out on the S3's native USB-C (all three hardware UARTs are
used by the scanners).

## Sectors

A scanner doesn't know its sector: the sector is the gateway RX pin its D6 is wired to, so
wiring is the only source of truth. (Scanners before 0.5.0 also sent a saved sector claim; the
gateway ignores it.) What the gateway checks is the scanner's chip ID, sent in every bucket:

- **Chip changed**: a different chip on a pin than the last one seen there (board swap or
  rewiring): `CHIP_CHANGED`, WARN (security), text "chip <new> replaced <old>".
- **Expected chip** (optional `expected_chip` per sector, 16 hex digits): any other chip on
  that pin is a `CHIP_MISMATCH`, logged as ERROR tagged `[SECURITY ERROR]` on first detection
  and then once a minute while it lasts; `suspect: true` on that sector's `rssi`, `adv` and
  `status`; the API binary sensor "Sector N chip mismatch" turns on. Data keeps flowing,
  labelled by the pin. When the expected chip is back: `CHIP_OK`, INFO (security).

## Settings the gateway keeps applied

Scanners boot with payload records off, passive scanning, default intervals and a 70 % budget,
and save none of these. The gateway holds what they should be (YAML options below) and, after
each scanner `BOOT` event, a new chip on a pin or a link gap, and then once a minute, compares
the scanner's `status` with it and sends only the differences, addressed to that chip. The
RSSI interval is mast-wide and only ever goes to all scanners at once. Settings changed by
MQTT command become the gateway's target too (until it reboots).

```yaml
sector_scanner:
  payloads: true        # payload records (adv topics) on
  active_scan: false    # scan requests: needed for scan_rsp, costs airtime
  budget: 70            # % of the line per tick (10-90)
  intervals:            # ticks of 200 ms; defaults shown
    rssi: 1             # 1-50, mast-wide
    payload: 1          # 1-50
    refresh: 50         # 1-3000
    status: 5           # 1-50
    counters: 50        # 1-3000
```

## Load and throttle

- **Scanner side**: each bucket's `load` (0 normal, 1 refresh slowed, 2 refresh off, 3 payloads
  off, 4 RSSI trimmed) goes to the "Sector N load" sensor and the retained `load` topic; the
  log says WARN for 1-3, ERROR for 4, INFO back at 0.
- **Gateway side**: every 10 s the gateway checks for an RX buffer more than three quarters
  full when read (`rx_overflow` in status: the UART driver doesn't report real overruns
  here), 3 or more bad frames, or 3 or more failed MQTT publishes. Two such windows in a row
  lower every scanner's `budget_pct` by 10 (not below 30) with a `BUDGET_LOWERED` event
  (LOAD, WARN); a clean minute raises it again by 10 (`BUDGET_RAISED`). The "Gateway load"
  sensor shows 0 normal, 1 under pressure, 2 budget lowered.

## MQTT output (layout v3)

All under `bletracker/<mast>/`, QoS 0. `<sector>` is the gateway's RX pin (0-2), which is the
scanner's sector. `t` is the gateway's clock when it handled the bucket, epoch **milliseconds**
(null until SNTP has set the clock). `chip` is the scanner's chip ID, 16 lowercase hex.

| Topic | Retained | When | Payload |
| --- | --- | --- | --- |
| `online` | yes | MQTT birth / last will / shutdown | `online` / `offline` |
| `info` | yes | at connect, and on `clear` | `{"format":3,"esphome":"2026.10.1","build":1793480556}` |
| `<sector>/rssi` | no | every bucket (5 Hz), or every RSSI interval when it's > 1 | batched RSSI, below |
| `<sector>/adv/<ADDR>` | no | each payload record (changed bytes, refreshes) | advert / scan response, below |
| `<sector>/status` | no | each status record (1 s) | scanner status + gateway link health, below |
| `<sector>/counters` | no | each counters record (10 s) | scanner totals since boot (`Counters` fields by name, `ignored` and `tx_1m_dropped` included) |
| `events` | no | every scanner and gateway event | event JSON, below |
| `security` | no | SECURITY-category events only | same JSON; this stream is the security record |
| `<sector>/ignore` | yes | each `IgnoreList` record (scanner 0.7.0+: at its boot, on a change, on request) | `{"t","chip","seq","paused","count","rules":[{"rule":"C1:7D:2B:00:00:00/24","saved":true,"hits":12}]}` |
| `<sector>/debug/tx_1m` | no | each `TxDrops` record (scanner 0.8.0+, `debug tx1m on`): after a second with dropped 1 m powers | `{"t","chip","seq","drops":[{"id":"AA:BB:CC:DD:EE:FF","random":true,"format":"ibeacon","raw_dbm":127,"tx_1m_dbm":127,"count":3}],"omitted":0}`; `format` `ibeacon`, `eddystone_uid` or `eddystone_url`; `raw_dbm` as advertised (Eddystone: at 0 m) |
| `<sector>/raw/<n>` | no | a record kind this gateway doesn't know (field `n` of `Record`) | the record's bytes as hex |
| `<sector>/online` | yes | first bucket / none for 3 s | `online` / `offline` |
| `<sector>/chip`, `load` | yes | on change | chip ID / load level. (`claim` and the v2 `scanner_sector` are no longer published; their retained values are cleared at connect) |
| `<sector>/flash`, `listening`, `client`, `test_image`, `active`, `payloads` | yes | on change | `on` / `off` |
| `<sector>/ant` | yes | on change | `int` / `ext` |
| `<sector>/debug` | yes | on change | `off` / `tx1m` (scanner debug output; older scanners: `off`) |

`<ADDR>` in topics is 12 upper-case hex digits, no colons; in payloads `AA:BB:CC:DD:EE:FF`.

RSSI, one message per bucket (records in the scanner's order, strongest mean first):

```json
{"t":1793476800123,"seq":100,"t_ms":20000,"tick_ms":200,"chan":0,"load":0,"chip":"38cd69b0ed39e516","suspect":false,
 "devs":[["C0:FF:EE:00:00:01",true,3,-67.0,-60,3,-59],["11:22:33:44:55:66",false,0,-67.5,-66,2,null]]}
```

Each `devs` entry: address, random (vs public), advert type (0 ind, 1 direct, 2 scan,
3 nonconn), mean RSSI (`sum / count`, one decimal, half away from zero), max RSSI, adverts
counted, advertised power at 1 m or null (none, or outside -100..+20 dBm: the scanner drops
it and counts it in `counters` `tx_1m_dropped`). `seq`, `t_ms`, `tick_ms`, `chan` (37-39, 0 = all)
and `load` are the bucket's. With `devs` empty the scanner heard nothing in that interval.

Advert / scan response (Theengs-style field names, so existing decoders work; no
device-specific decoding here):

```json
{"id":"C0:FF:EE:00:00:01","mast":"garage","sector":0,"chip":"38cd69b0ed39e516","t":1793476800123,"suspect":false,
 "kind":"adv","rssi":-61,"random":true,"adv_type":3,"refresh":false,"age_ms":0,
 "data":"0201060709...","name":"T\"Ä\"","manufacturerdata":"4c000215aabb","servicedata":"010203",
 "servicedatauuid":"0x181a","txpower":-4,"uuids":["0x180f","0xfeaa"]}
```

- `kind` `adv` or `scan_rsp`; `data` the raw AD bytes (hex); `refresh` an unchanged re-send;
  `age_ms` how long the scanner held it back (`age_ticks × tick_ms`).
- Split out of `data`, each only when present: `name` (complete name preferred over shortened;
  invalid UTF-8 bytes become `?`), `manufacturerdata` (hex, company ID first as sent),
  `servicedata` + `servicedatauuid` (the first 16-, 32- or 128-bit service data),
  `txpower` (dBm), `uuids` (every listed service UUID: `0x180f`, `0x12345678`, or the
  128-bit form). A truncated AD structure ends the parsing; `data` still has everything.

Status (each Status record, plus the gateway's view of the link):

```json
{"t":…,"chip":"38cd69b0ed39e516","seq":100,"pin_sector":0,"suspect":false,"lost":0,"bad":0,"rx_overflow":0,
 "version":"0.4.0","ext_antenna":false,"listening":true,"active_scan":false,"payloads":true,"flash_mode":false,
 "client":false,"test_image":false,"adverts":123,"dropped":0,"devices":3,"load_reasons":0,"line_peak_pct":61,
 "budget_pct":70,"intervals":{"rssi":1,"payload":1,"refresh":50,"status":5,"counters":50},"baud":115200}
```

`lost`: buckets missed (seq gaps) since the gateway booted; `bad`: frames dropped (COBS, CRC or
protobuf); `rx_overflow`: times the RX buffer was over three quarters full. The scanner
fields are as in `bletracker.proto`.

Counters: `{"t","chip","seq"}` plus every `Counters` field by its proto name.

Events (scanner and gateway alike):

```json
{"t":…,"source":"scanner","sector":0,"chip":"38cd69b0ed39e516","category":"SECURITY","severity":"INFO",
 "code":"BOOT","value":1,"value2":7,"cmd_seq":0,"text":"power-on"}
```

Scanner codes are `Event.Code` names (PROTOCOL.md "Event codes"). Gateway codes (`source`
`gateway`, `sector` null for mast-wide ones):

| code | category / severity | value, value2 |
| --- | --- | --- |
| `CHIP_MISMATCH` | SECURITY, ERROR | -, pin sector; text names the expected chip |
| `CHIP_OK` | SECURITY, INFO | -, pin sector; the expected chip is back |
| `CHIP_CHANGED` | SECURITY, WARN | text "chip <new> replaced <old>" |
| `CMD_NO_ACK` | COMMAND, WARN | `cmd_seq` = the command's seq |
| `IGNORE_MISMATCH` / `IGNORE_MATCH` | SECURITY, WARN / INFO | online scanners compared; the scanners' ignore lists (rules and saved flags, not hits) differ / match again; text gives each sector's rule count |
| `BUDGET_LOWERED` / `BUDGET_RAISED` | LOAD, WARN / INFO | new budget % |

The log shows every event at its own severity as `[CATEGORY SEVERITY] sector N scanner|gateway: CODE text`.

Retained topics are cleaned up by the gateway: at every MQTT connect (boot or broker
reconnect) it deletes each sector's state topics (and the pre-release `scanner_sector` topic) and
republishes them from the next bucket, so nothing from a scanner that's gone survives. A
sector that stops sending only turns `<sector>/online` to `offline`. A retired or renamed
mast's topics can only be removed on the broker (EMQX: `emqx ctl retainer clean bletracker/<mast>/#`).

Watch the stream from a PC:

```bash
mosquitto_sub -h <broker> -u <user> -P <pass> -t 'bletracker/#' -v
```

## Commands

Publish to `bletracker/<mast>/<sector>/cmd` to reach that sector's scanner (the chip last
seen on its RX pin; ignored with a warning until one has been seen), or to
`bletracker/<mast>/all/cmd` for every scanner on the mast. Plain text, or JSON
`{"cmd":"payloads on"}`; the same words as `../scanner_fw/tools/decode_frames.py --cmd`:

| Payload | Effect |
| --- | --- |
| `listen on` / `listen off` | start / stop scanning (buckets keep coming) |
| `flash on` / `flash off` | open (10 min) / close flash mode for a BLE firmware update |
| `ant ext` / `ant int` | external / onboard antenna (saved in the scanner) |
| `reboot` | restart the scanner |
| `payloads on` / `payloads off` | payload records (`adv` topics) on / off |
| `active on` / `active off` | active scanning (scan responses) on / off |
| `budget <10-90>` | the scanner's byte budget, % of the line per tick |
| `intervals rssi=N payload=N refresh=N status=N counters=N` | any subset; `rssi` only on `all/cmd` |
| `ignore <addr>[/bits\|/mask] [save]` | only on `all/cmd` (the ignore list is mast-wide), scanner 0.6.0+: drop that address (or range; `*` bytes allowed, e.g. `c1:7d:2b:*:*:*`) until the scanners reboot, or with `save` for good |
| `unignore <addr>[/bits\|/mask]` | only on `all/cmd`: remove that rule (same address and mask) |
| `ignore clear boot` / `saved` / `all` | only on `all/cmd`: remove the rules kept until reboot / the saved ones / all of them |
| `debug tx1m on` / `debug tx1m off` / `debug off` | scanner 0.8.0+, on `<sector>/cmd` or `all/cmd`: per-second summary of adverts whose 1 m power the scanner dropped, on `<sector>/debug/tx_1m`. Off at every scanner boot, and the gateway doesn't turn it back on |
| `ignore list` | scanner 0.7.0+, on `<sector>/cmd` or `all/cmd`: the scanner sends its rules, published on `<sector>/ignore`. The gateway asks by itself when it hasn't seen a scanner's list (e.g. after the gateway restarts) |

Each command gets a gateway `seq`; the scanner answers with a `CMD_OK` or `CMD_REJECTED`
event (on `events`). One command is on the wire at a time; the next goes after the ack, or
after 2 s with a `CMD_NO_ACK` warning. The DEBUG log shows each command's bytes in hex,
which match `decode_frames.py --cmd ... --seq N`.

Commands for the gateway itself go to `bletracker/<mast>/cmd`:

| Payload | Effect |
| --- | --- |
| `reboot` | restart the gateway |
| `clear` | delete and republish all of the mast's retained topics |

## Self-test

With `self_test: true` (the default) the gateway checks itself once at boot, without touching
MQTT or the scanners: the contract's command test vectors must encode byte for byte, and
sample buckets (built and framed by the reference protobuf code in `tools/make_selftest.py`,
covering every record kind, an unknown record kind and field, the retired sector claim field,
a lost bucket, a bad CRC, odd advert names and a truncated AD structure) must
produce exactly the expected MQTT messages. The result goes to the log and to the "Self test"
text sensor, e.g. `PASS: commands 16/16, messages 16/16`; a FAIL logs each differing message.
After changing the JSON layout or the test vectors, regenerate:

```bash
python tools/make_selftest.py        # writes components/sector_scanner/selftest_data.h
```

## Home Assistant entities

Over the ESPHome API, per sector: load level, lost buckets, bad frames (one at boot is
normal, as the first frame is usually partial), devices heard, "chip mismatch" (problem
binary sensor, `expected_chip` only), the scanner's chip ID, and buttons "flash mode" and "reboot scanner". For the
gateway: "Gateway load", "Self test", IP and MAC address.
